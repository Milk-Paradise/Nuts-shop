# CLAUDE.md — catalog-backend

Инструкции для агентов, работающих в этом репозитории. Пишется заново после
разделения монорепозитория (23 сентября 2026); старый общий `CLAUDE.md`
описывал раскладку `apps/backend` и больше не действует.

Перед любой задачей по Medusa — сначала загрузить medusa-dev скилы
(`building-with-medusa`, при работе с админкой `building-admin-dashboard-customizations`),
до написания кода.

## Архитектура

### Паттерн: порты и адаптеры, порты берём у Medusa

Внешние провайдеры подключаются к модулям, а не к приложению. Ядро не знает,
через кого списываются деньги и кто везёт посылку — оно знает контракт.

Это гексагональная архитектура, и Medusa v2 реализует её сама. **Порты писать
не надо — они уже есть** в виде абстрактных классов фреймворка:

| Что | Порт (контракт) | Наши адаптеры |
|---|---|---|
| Оплата | `AbstractPaymentProvider` | `providers/payment-yookassa-runtime`, `providers/payment-e2e` |
| Доставка | `AbstractFulfillmentProviderService` | `providers/fulfillment-cdek`, Озон, встроенный `fulfillment-manual` |
| Уведомления | `AbstractNotificationProviderService` | `modules/notification-smtp`, `modules/notification-e2e` — лежат в `modules/`, но это `ModuleProvider`, а не модули с таблицами |
| Файлы | провайдер File Module | `@medusajs/medusa/file-s3` |
| Авторизация | провайдер Auth Module | стандартный `emailpass` |

**Свой модуль оплаты, доставки, авторизации или уведомлений писать нельзя.**
Через стандартные Payment и Fulfillment Module работают корзина, чекаут,
заказы, возвраты и платёжные сессии ядра. Собственный порт означает, что ядро
адаптер не увидит, и переписывать придётся весь checkout, а не только оплату.
Это конкретное применение общего правила проекта: standard first, custom only
if needed.

### Поток обязателен, слои не обходим

```
Module (данные + CRUD, изолирован)
  ↓
Workflow (бизнес-логика, шаги, компенсации при откате)
  ↓
API Route (валидация + HTTP, без логики)
```

- Любая мутация — через workflow. Роут не вызывает сервис модуля напрямую.
- Бизнес-валидация и проверка прав — в шагах workflow, не в роуте.
- Модуль остаётся простым: CRUD по своим таблицам, без бизнес-логики.
- Только `GET`, `POST`, `DELETE` — никогда `PUT`/`PATCH`.
- Межмодульные данные — `query.graph()`; фильтрация по полям связанного
  модуля — `query.index()`.

**Три первых правила сейчас в коде нарушены, и это известно.** Аудит
архитектуры (октябрь 2026) нашёл 10 записывающих endpoint'ов из 38, которые
пишут минуя workflow, 8 подписчиков из 10, обходящих workflow, и бизнес-правила
в `src/api` вместо шагов. Приводится в порядок AIL-148; правило при этом
остаётся жёстким — исключения для «одной простой записи» решено не вводить.

Писать новый код по нарушенному образцу нельзя: на вопрос «а вон там же
напрямую» ответ — «там задача на исправление, а здесь новый код».

Отдельная ловушка: **файл в `src/workflows` не обязательно workflow.** Три из
нарушителей лежат именно там, оставаясь обычными функциями. Признак настоящего
workflow — `createWorkflow`, а не путь файла.

`query.index()` в репозитории пока не вызывается ни разу, а `src/links` пуст:
связи с сущностями ядра хранятся текстовыми `order_id`/`cart_id`/`customer_id`.
Отсюда ручные joins и отсутствие ссылочной целостности. Это нерешённый вопрос
(AIL-150), а не образец для подражания.

### Новая интеграция: адаптер или свой модуль

Решается одним вопросом — **есть ли у Medusa абстрактный класс под эту роль**:

- **Есть** → адаптер в `src/providers/<имя>`, реализует абстрактный класс.
  Ничего своего в чекаут и заказы тянуть не нужно.
- **Нет** (ERP, поисковый индекс, произвольный внешний сервис) → свой модуль
  в `src/modules/<имя>`. Образец — `modules/moysklad-integration`.

Канон модуля-интеграции:

| Файл | Роль |
|---|---|
| `client.ts` | HTTP-клиент внешнего API — **единственное место, знающее их формат** |
| `credentials.ts` | реквизиты (см. раздел про секреты ниже) |
| `service.ts` | модульный сервис: CRUD по своим таблицам |
| `models/` | свои таблицы, включая состояние синхронизации |
| `retry-schedule.ts` и подобные | политики чистыми функциями, тестируются без сети |
| `migrations/` | схема |

Изоляция `client.ts` — не косметика: именно она позволяет тестам не ходить в
сеть, а типам чужого API не утекать в workflow.

**Эта изоляция сейчас не соблюдается.** `MoyskladClient` импортируют восемь
файлов за пределами своего модуля, `CdekClient` и `OzonClient` — десять
(workflow'ы, задание синхронизации, админ-роут). Внешний тип уже утёк:
`MoyskladPayment` фигурирует в шаге `create-moysklad-incoming-payment.ts:5`.
Исправляется AIL-147.

Почему так вышло, и почему это не оправдание для нового кода: порт
`AbstractFulfillmentProviderService` покрывает жизненный цикл отправления —
расчёт, создание, отмену, возврат, — но у него нет методов для синхронизации
ПВЗ, списка тарифов в админке, скачивания этикетки и проверки реквизитов. Для
них место в порту появляется не форком Medusa, а расширением собственного
адаптера — см. «Порт перевозчика расширяем своими методами» ниже.

### Куда подключается внешний мир

- внешнее событие пришло к нам → `src/subscribers/`, и подписчик **вызывает
  workflow**, а не делает работу сам (сейчас так делают только два подписчика
  из десяти — refund и payment-status; остальные дёргают шаги и сервисы
  напрямую, AIL-148);
- спрашиваем их по расписанию → `src/jobs/`;
- вебхук от них → роут + workflow (`workflows/process-cdek-webhook.ts`);
- операция может упасть на полпути → workflow со шагами и компенсацией;
- попытку надо повторять → **своя таблица состояния + job повтора**.

Последнее — жёсткое правило, а не вкус: любая запись в Cart двигает его
`updated_at`, поэтому bookkeeping вида «уже отправили письмо об этой корзине»
в metadata корзины сам ломает логику обнаружения бездействия. Состояние
повторов живёт в отдельной таблице по `cart_id` (или `order_id`).

### Подстановка адаптера — только в `medusa-config.ts`

`medusa-config.ts` — единственное место, где называется конкретный провайдер:

```ts
{
  resolve: "@medusajs/medusa/payment",
  options: { providers: [{ resolve: "./src/providers/payment-yookassa-runtime", id: "yookassa" }] },
}
```

Это единственное место, где адаптер **подставляется**, и это правило кодом
подтверждается: все `resolve` провайдеров сосредоточены здесь.

А вот следствие «замена провайдера — правка одной записи» верно только для
оплаты. **Для доставки оно неверно**, и это надо знать до того, как обещать
такую замену: прикладной код знает ключи перевозчиков, форму их payload
(`cdekData`, `ozonData`), форматы тарифов и набор возможностей. Ветвления по
ключу живут в `api/catalog/shipping/utils.ts`, `workflows/get-delivery-fulfillment-label.ts`,
`workflows/resolve-shipping-return-request.ts` и в признаках заказа. Один из
них уже даёт ошибку (AIL-144), другой тихо примет третьего перевозчика за
Озон: `provider_key === CDEK ? "cdek" : "ozon"`.

Идентификаторы (`cdek_cdek`, `ozon_ozon`) берутся **только** из констант
`src/modules/shipping-provider-registry/provider-keys.ts`. Литералом их писать
нельзя — сейчас так сделано в восьми местах. Резолвить адаптер по имени в обход
конфига нельзя; получать уже зарегистрированный адаптер из контейнера —
можно и нужно, см. следующий раздел.

### Порт перевозчика расширяем своими методами

Medusa регистрирует **наш класс адаптера целиком** в контейнере приложения:

```js
container.register({ ["fp_" + key]: asFunction((cradle) => new klass(cradle, options)) })
```

(`@medusajs/fulfillment/dist/loaders/providers.js:10`)

Ядро вызывает только методы порта, но сам объект доступен прикладному коду
через `resolve("fp_" + PROVIDER_KEY)`. Отсюда правило для всего, что в порт
Medusa не укладывается:

**адаптер объявляет метод сверх порта, и прикладной код ходит в адаптер — не в
`CdekClient`/`OzonClient` напрямую.** Клиент перевозчика остаётся деталью
реализации внутри модуля.

Так выглядит «порт перевозчика уникален» без форка фреймворка: ядро продолжает
работать с `AbstractFulfillmentProviderService`, а синхронизация ПВЗ, тарифы,
этикетки и проверка реквизитов получают единую дверь. Замена перевозчика тогда
действительно становится правкой конфига.

Возврат — особый случай, и не тот, которым кажется. Метод
`createReturnFulfillment` в порту есть, у СДЭК он оставлен заглушкой, и это
выглядит как необъяснимый обход. На самом деле **к этой заглушке нет пути**:
возвратный процесс Medusa (`createReturnFulfillmentWorkflow`,
`confirmReturnRequestWorkflow` и родственные) в проекте не вызывается ни разу.
Возврат здесь свой — заявка `shipping_return_request`, модерация,
идемпотентность по `business_action_id` вида `return:<id>`, — и ядро в нём не
участвует, поэтому портовый метод никто не вызывает.

Отсюда правило: возврат к перевозчику идёт **своим методом адаптера**
(`createReturnShipment`), как и прочие вызовы, которых в порту нет. Переходить
на возвратный процесс ядра ради того, чтобы «использовать порт», — отдельное
продуктовое решение: оно меняет модерацию заявок, а не только адрес вызова.

### Тестовый адаптер — часть контракта

`payment-e2e` и `notification-e2e` существуют не как костыль, а как выполнение
правила «никакой тест не ходит в реальный внешний сервис». Новой интеграции
полагается тестовый адаптер того же порта, а не мок внутри теста.

### Раскладка плоская по типу — так требует фреймворк

`src/modules`, `src/providers`, `src/workflows`, `src/subscribers`, `src/jobs`,
`src/api`, `src/links`, `src/admin`.

Не раскладывать по `core/` и `infrastructure/` внутри модуля, как предлагают
общие описания гексагональной архитектуры: Medusa **автозагружает по
соглашению** — workflow из `src/workflows`, подписчиков из `src/subscribers`,
задания из `src/jobs`, роуты из `src/api`. Workflow, положенный в
`modules/<имя>/core/workflow/`, фреймворк не найдёт и не зарегистрирует.
Чистота достигается изоляцией `client.ts` и чистыми функциями-политиками, а не
вложенностью папок.

### Секреты провайдеров: один механизм

Реквизиты внешних провайдеров хранятся в своём модуле в шифрованном виде,
расшифровка не покидает модуль. Шифрование секретов — **одна реализация на
репозиторий**: `src/lib/secret-crypto.ts`. Новые записи имеют формат `v2` и
всегда используют `SECRET_ENCRYPTION_KEY` — канонический base64-ключ ровно на
32 байта.

Три прежние переменные существуют только для совместимого чтения записей
старого формата `v1`:

| Модуль | Переменная | Формат ключа |
|---|---|---|
| `modules/payment-provider-config/crypto.ts` | `PAYMENT_PROVIDER_CONFIG_ENCRYPTION_KEY` | base64, ровно 32 байта |
| `modules/shipping-provider-registry/credentials.ts` | `SHIPPING_PROVIDER_CONFIG_ENCRYPTION_KEY` | любая строка → `sha256` |
| `modules/moysklad-integration/credentials.ts` | `MOYSKLAD_ENCRYPTION_KEY` | любая строка → `sha256` |

При наличии нового ключа успешное чтение старой записи немедленно сохраняет
её в `v2`. Пока `SECRET_ENCRYPTION_KEY` ещё не добавлен в окружение, старые
записи продолжают читаться прежними ключами, но новые реквизиты сохранить
нельзя. Если реквизиты МойСклад не расшифровываются прежним ключом, ошибка
явно просит ввести их заново, вместо молчаливой потери.

### Что проверяется барьером, а что остаётся текстом

Правило, которое можно выразить в линтере или типах, должно быть там, а не
только здесь: текст не остановил ни одного из трёх расхождений выше. Общее
правило о том, что проверяемое должно проверяться, — в разделе «Правила
построения кода».

**Барьером (`eslint.config.ts`, уровень `error`):**

- `createCipheriv`/`createDecipheriv` не импортируются нигде, кроме
  `src/lib/secret-crypto.ts`.
  Хеши, HMAC и UUID из `crypto` правило не задевает: ограничены ровно две
  функции шифрования.

**Типами** — сильнее всего: если внешний формат живёт только в `client.ts`,
типы чужого API физически не могут утечь в workflow.

**Текстом** — то, что в синтаксис не выразить: когда адаптер, а когда модуль;
почему состояние повторов в своей таблице; почему политики — чистые функции.

## Правила построения кода

Раздел «Архитектура» отвечает на вопрос «как устроено». Этот — на вопрос «куда
положить то, что я сейчас пишу», чтобы ответ не приходилось угадывать по
ближайшему файлу.

### Сначала искать, потом писать

Перед новым кодом — найти существующий. Это не вежливость, а главная причина,
по которой здесь уже три несовместимые реализации шифрования и две схемы работы
с реквизитами перевозчика. Каждая из них появилась потому, что автор не нашёл
предыдущую.

Проверять по порядку: есть ли готовое в Medusa (стандартный модуль, Store/Admin
API, core-flow); есть ли уже в этом репозитории функция, шаг или политика,
делающая то же; можно ли расширить существующее вместо второй реализации рядом.
Кастомный код — только когда стандартного не хватает, и в коммите видно, чего
именно не хватило.

### Направление зависимостей

```
api  →  workflows  →  modules  →  providers (адаптеры)
                   ↘  lib / utils  ↙
```

Стрелки односторонние. **`modules`, `workflows`, `providers`, `jobs` и
`subscribers` не импортируют из `src/api` никогда.** Сейчас таких импортов
восемь — workflow шага чекаута и синхронизация Meilisearch тянут код из `api`.
Следствие буквальное: правка файла в `api` одновременно меняет HTTP-ответ,
checkout и поисковый индекс. Исправляется AIL-149 (барьер) и AIL-148.

Обратная сторона того же правила: `api` не импортирует `src/workflows/steps/**`.
Роут запускает workflow целиком, а не дёргает его шаг — иначе шаг исполняется
без композиции, без компенсации и без событий.

### Куда положить новый код

| Что пишу | Куда | Признак, что место верное |
|---|---|---|
| Таблица и CRUD по ней | `src/modules/<имя>/` | есть `models/`, `migrations/`, `service.ts` |
| Интеграция с внешним сервисом, под который у Medusa есть порт | `src/providers/<имя>/` | наследует `Abstract*`-класс, подставляется в `medusa-config.ts` |
| Интеграция без подходящего порта | `src/modules/<имя>/` с `client.ts` | формат чужого API не виден снаружи модуля |
| Бизнес-операция, меняющая состояние | `src/workflows/` | `createWorkflow`, шаги, компенсация |
| Шаг такой операции | `src/workflows/steps/` | падает — и откат предыдущих шагов происходит сам |
| HTTP-граница: валидация ввода, форма ответа | `src/api/` | уберёшь роут — бизнес-правило не потеряется |
| Расписание | `src/jobs/` | запуск по времени, тело — вызов workflow |
| Реакция на событие | `src/subscribers/` | тело — вызов workflow, не работа |
| Чистая функция без контейнера и сети | `src/utils/` | тестируется без моков вообще |
| Код, нужный нескольким слоям, со своими зависимостями | `src/lib/` | не имеет таблиц, но нужен и в `api`, и в `workflows` |

Правило для `lib` против `utils`: в `utils` — то, что можно вызвать из любого
места без подготовки (`availability.ts` — расчёт статуса наличия, единственный
житель). В `lib` — то, что нужно нескольким слоям, но тянет зависимости.

**`lib` соблюдает это правило не полностью:** `cms-content.ts` — gateway к
Strapi, `pickup-point-snapshot-cache.ts` — работа с S3. По правилу выше это
интеграции, и место им в модуле. Решение по ним — AIL-150; до него не
добавлять в `lib` новых интеграций с внешними сервисами.

### Чего не делать в API-слое

API переводит HTTP в вызов и ответ в DTO. Он **не** решает, можно ли купить
товар, какую цену взять, разрешена ли отмена и какой провайдер обслужит
отправление.

Сейчас решает: допустимость товара и выбор варианта — `api/catalog/utils.ts`,
сценарий оплаты и блокировка — `api/catalog/handlers.ts:459`, права на заказ и
возможность отмены — `api/store/account/orders/utils.ts`, выбор провайдера и
деградация ошибок — `api/catalog/shipping/utils.ts`. Это причина, по которой
`workflows` и `modules` вынуждены импортировать `api` — правило понадобилось им
самим.

Куда правило переезжает: влияющее на мутацию — в шаг workflow; политика чтения,
нужная нескольким местам, — в `lib` или в сервис модуля; формирование ответа
остаётся в `api`.

### Имена и границы должны быть честными

`shipping-provider-registry` называется реестром, а держит восемь моделей:
реквизиты, видимость, ПВЗ, снимки расчётов, заявки на возврат, отправления,
упаковку и события вебхуков — плюс оба HTTP-клиента перевозчиков. Имя описывает
десятую часть ответственности, и из-за этого в него продолжают добавлять всё
подряд.

Правило: если модуль перестал соответствовать имени — переименовать или
разделить, а не дописывать. Имя в этом коде — единственная подсказка о границе
ответственности, потому что папки плоские по требованию фреймворка.

### Правило, которое можно проверить, должно проверяться

Текст не остановил ни одного расхождения, найденного аудитом: все шесть
нарушенных правил были написаны здесь до того, как их нарушили. Поэтому новое
правило вводится вместе с проверкой, если её можно выразить: запрет импорта,
запрет пути, запрет литерала.

Как вводить: новое правило — `warn`, повышение до `error` после устранения
нарушений. Правило с нулём нарушений вводится сразу `error` — оно ничего не
ломает и охраняет уже достигнутое. Перечень кандидатов и текущее число
нарушений по каждому — AIL-149.

Сильнее линтера работают типы: если внешний формат живёт только в `client.ts`,
типы чужого API физически не могут утечь в workflow — нарушение становится
невыразимым, а не запрещённым. Там, где выбор есть, предпочитать тип правилу.
Но тип тоже надо держать узким: `OzonCredentials = ShippingProviderCredentials
| string` разрешает и расшифрованный объект, и шифротекст — из-за этого
проверка типов не видит разницы, а читающий человек ошибается (AIL-150).

Чего проверкой не выразить — остаётся текстом и живёт в этом файле: когда
адаптер, а когда модуль; почему состояние повторов в своей таблице; почему
политика — чистая функция. Полуработающее правило не вводить: оно даёт ложное
чувство защиты. Проверка «записывающий роут обязан звать workflow» по пути
файла именно такова — три нарушителя лежат внутри `src/workflows`.

### Предложение владельцу: ссылки custom-модулей на ядро Medusa

**Статус: ждёт утверждения владельцем.** Предлагаем пока оставить строковые
`*_id`-ссылки на core-сущности, а не переводить их на module links. Сейчас в
`src/links` нет рабочих связей, Index Module не подключён, а существующие
сценарии читают core-сущность по известному идентификатору; переход не решает
актуальную продуктовую потребность и добавит миграции, создание/удаление links
и новый путь запросов.

Пересмотреть решение нужно до первой функции, которой требуется фильтровать
custom-сущности по полям связанного core-модуля (`query.index()`), получать
связанные сущности одним graph-запросом в списковом API, либо гарантировать
каскадную очистку при удалении core-сущности. Тогда оформить отдельную задачу:
определить cardinality и delete cascade для каждой связи, добавить link-файлы
и Index Module, миграции и запись/чтение links; строковые ID не смешивать с
новым механизмом без явного плана перехода.

## Команды

Используем Node не ниже 20; для этого репозитория `package.json` требует
`>=22.13.0`, поэтому штатный выбор — Node 22.23.2:

```sh
export PATH="$HOME/.nvm/versions/node/v22.23.2/bin:$PATH"
ln -s ../../../node_modules node_modules
cp .env.template .env
```

Node 16 в shell по умолчанию не годится: на нём линтер падает с
`structuredClone is not defined`; это несовместимость рантайма, а не ошибка
исходников. В свежем worktree нет ни `node_modules`, ни `.env`: симлинк и
локальный файл окружения создаются перед любыми CLI-командами.

Обычный цикл разработки:

```sh
# В checkout catalog-infra: только зависимости разработки.
docker compose up -d postgres redis meilisearch minio

# В этом репозитории: сам backend работает с хоста.
npm run dev
npm run test:unit
npm run test:integration:http
npm run test:integration:modules
npm run test:unit -- src/utils/__tests__/availability.unit.spec.ts
npx medusa db:migrate
npx medusa user --email admin@example.test --password '<пароль>'
```

Миграции и создание администратора тоже запускаются с хоста. Для обычной
разработки Docker-образ backend не пересобираем: он нужен только для
smoke-проверки полного пакета.

## Линтинг

Гейт валят только ошибки: предупреждения печатаются, но не делают команду
неуспешной. Новое правило сначала вводим как `warn`; перевод в `error`
допустим только после устранения всех уже существующих нарушений.
`eslint-disable` всегда сопровождается причиной на той же или предыдущей
строке.

`npm run build` запускает линтер через `medusa build`; падение сборки на нём
не является отдельной ошибкой сборки. Сообщение `Linting skipped` означает,
что гейт отказался проверять код, а не что проверка пройдена.

Есть сознательно красный барьер: `no-restricted-imports` запрещает
`createCipheriv` и `createDecipheriv`. Сейчас он даёт ровно шесть ошибок — по
две в `payment-provider-config/crypto.ts`,
`shipping-provider-registry/credentials.ts` и
`moysklad-integration/credentials.ts`. Это единственное отступление от
правила «сначала warn»: `lint` — первая стадия CI, а `build:backend` зависит
от неё, поэтому образ не создаётся до закрытия AIL-120. Не ослаблять и не
исправлять этот барьер попутно.

## Тесты — только на моках

Ни unit-, ни integration-тест не должен обращаться к реальному МойСклад,
СДЭК, Ozon, YooKassa или SMTP. Интеграционный тест проверяет границу нашего
приложения с локальными Postgres и Redis, а не доступность чужого API: отказ
внешнего сервиса не доказывает правильность логики.

`payment-e2e` и `notification-e2e` — тестовые адаптеры стандартных портов,
а не временный мок внутри теста. При `E2E_RUN=true` первый добавляется к
списку платёжных провайдеров, а второй заменяет SMTP; при `NODE_ENV=test`
уведомления также идут в `notification-e2e`. Клиенты доставки и МойСклад в
тестах должны быть замоканы так же. Если моковый сценарий нашёл ошибку, это
основание для задачи, а не для подгонки теста до зелёного результата.

После прогона проверьте, что тесты не пытались выйти в сеть:

```sh
set -o pipefail
npm run test:unit 2>&1 | tee /tmp/catalog-backend-tests.log
rg -n 'ENOTFOUND|ECONNREFUSED|https?://' /tmp/catalog-backend-tests.log
```

Любое совпадение расследуется; отсутствие совпадений имеет смысл только
вместе с успешным тестовым прогоном.

## Выкатка

Агент доводит изменение до merge request и останавливается. Слияние в `main`
и ручную выкатку выполняет владелец.

В `.gitlab-ci.yml` стадии идут так: `lint`, `typecheck`, `unit`,
`integration`, `build`, `deploy`. Для `prod`, `qa-a` и `qa-b` подключён один
компонент `catalog-infra/deploy`; его deploy-job имеет `when: manual`, так что
сам merge ничего не выкатывает.

В образе нет изменяемого тега для выкатки: build записывает digest в
`BACKEND_IMAGE_DIGEST`, а CI передаёт в компонент
`$CI_REGISTRY_IMAGE@$BACKEND_IMAGE_DIGEST`. Компонент проверяет формат
`@sha256:…` и записывает эту неизменяемую ссылку в поле `dockerImage`
приложения Dokploy. Переменной `BACKEND_IMAGE` в текущем пайплайне нет.

Зелёный deploy-job и визуальный осмотр страницы не считаются проверкой.
После времени выкладки смотрите Loki в Grafana владельца: dashboard uid

## Правила Medusa, которые иначе нарушаются

- Цены хранятся как есть: `49.99` — это `49.99`, не копейки. Не умножать и не
  делить на 100.
- `query.graph()` получает связанные данные. Если нужна фильтрация по полю
  связанного модуля, используйте `query.index()`; не заменяйте её JS-фильтром
  после чтения.
- Имя модуля — camelCase. Дефис в имени модуля даёт runtime-ошибку.
- HTTP-методы — только `GET`, `POST`, `DELETE`; `PUT` и `PATCH` не использовать.
- Мутация идёт через workflow, а бизнес-валидация — в его шагах; это правило
  уже описано в разделе «Архитектура» и здесь не дублируется.

### Публичные маршруты витрины — только под `/store`

Новый публичный маршрут каталога создаётся в `src/api/store/catalog/*`, а не в
`src/api/catalog/*`. Пространство `/store` даёт готовую проверку
publishable-ключа и CORS из `storeCors`, и ровно поэтому витрина ходит одной
дверью. Маршрут, заведённый мимо `/store`, этих проверок не получает, и
отсутствие их не видно ни в коде роута, ни в ответе.

Реализация при этом живёт в `src/api/catalog/`: `handlers.ts` и соседние
`utils.ts` — общий код, а `route.ts` в пространстве `/store` это одна строка
реэкспорта нужного обработчика. Валидатор запроса регистрируется на
`/store/catalog/...` в `src/api/middlewares.ts`; забыть его — значит отдать
обработчику непроверенный ввод.

Исключения ровно два, и оба обоснованы:

- `/catalog/config` — отдаёт publishable-ключ, который под `/store` требуется
  на входе. Перенести его — замкнуть круг: витрина не сможет получить ключ,
  чтобы войти в `/store`.
- вебхуки (`/catalog/webhooks/*`, `/hooks/*`) — их зовут внешние сервисы, у
  которых нет и не может быть ключа витрины. Внешний адрес вебхука меняется
  только по согласованию с провайдером.

## Грабли этого проекта

- `MEDUSA_FF_RBAC` недостаточно оставить на автоопределение ядра: модуль
  `rbac` зарегистрирован в `medusa-config.ts` явно и вынесен из ветки
  `isTest`. Держите `MEDUSA_FF_RBAC=true` в `.env` синхронно с
  `.env.template`: host CLI читает именно этот файл.
- Игнорируемый `.env` не попадает в новый git worktree. До `cp .env.template
  .env` ошибки CLI часто выглядят не связанными с задачей.
- Любая запись в Cart меняет `updated_at`. Поэтому отметка «письмо по этой
  корзине уже отправлено» хранится в отдельной таблице
  `abandoned_cart_reminder` по `cart_id`, со снимком времени корзины, а не в
  её metadata: иначе сама отметка имитирует активность.
- `fulfillment_status` и `payment_status` заказа вычисляет Query, это не
  колонки для `updateOrders()`. Классификацию по ним держим чистой функцией
  `classifyOrderBucket` и тестируем на синтетических заказах.
- При расчёте доставки Medusa строит pricing context без
  `shipping_address.address_1` и `address_2`: провайдеру доступны город,
  страна, регион/провинция и индекс. Это ограничение ядра, не СДЭК или Ozon.
- После унификации ПВЗ снимок кэшируется по SHA-256 нормализованных `city`,
  `address`, `carrier` и `provider_keys`; сохранённый снимок дополнительно
  сверяется с полным request. При добавлении нового фильтра добавьте его в
  `PickupPointSnapshotRequest` и ключ, иначе он не сможет разделить кэш.
- Checkout возвращает `409`, если доступный вариант доставки остался без
  выбранного shipping method. Это серверская защита от вызова API в обход
  клиентской блокировки кнопки, а не тихий fallback.
- Признак зарегистрированного покупателя — `customer.has_account`, а не
  наличие `customer_id` или email: гостевой checkout тоже создаёт Customer.
- `addToCartWorkflow` и `updateLineItemInCartWorkflow` всегда проверяют
  остаток. При намеренном пропуске проверки (слияние корзин) пишите line items
  через сервис `Modules.CART`, затем запускайте `refreshCartItemsWorkflow`.
- Статус наличия не хранится отдельным полем. Он вычисляется из стандартного
  inventory в `src/utils/availability.ts` функциями `variantAvailability` и
  `productAvailability`.
- Нельзя выводить из кода, что в магазине уже были пользователи или
  продуктовые данные; поэтому не заявляйте заранее, что миграция старых
  записей либо обратная совместимость не нужны. При этом схемы конфигурации в
  БД существуют: например, реестр доставки хранит шифрованные реквизиты
  провайдеров. Не повторяйте старое неверное утверждение, что реестры хранят
  только несекретную конфигурацию.
